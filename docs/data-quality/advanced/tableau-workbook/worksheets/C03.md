## Question and decision

Which references stay in or move between published ABC classes and an extract-volume classification? A 3×3 highlight table separates agreement on the diagonal from off-diagonal differences. It supports choosing a classification basis suitable for a future slotting study, not overwriting the published classes.

## Data, formulas and web rebuild

[abc_comparison.csv](../../public/abc_comparison.csv): one demanded reference, primary key reference_id. reference_id/published_abc/derived_abc are String dimensions. customer_units/disagrees are integer measures. rank is an ordinal; cumulative quantities/denominator are nonadditive. Source populations: 208 references / 228195 customer units.

1. Connect the CSV independently. Rows: published_abc; Columns: derived_abc, both discrete and ordered A/B/C. Use Square/Highlight Table marks.
2. Rebuild `Distinct References = COUNTD([reference_id])`; put it on Color and Label. The published label “Distinct References” is observed; the internal calculated-field expression is not exported. [COUNTD reasoning](../CALCULATION_REFERENCE.md#fixed-denominators-and-counts).
3. Put SUM(customer_units) on Tooltip with both class labels and distinct-reference count. This tooltip field is observed; individual values were not exhaustively checked. Count and unit volume answer different questions.
4. A reference/ABC/disagreement filter is possible future guidance, not a confirmed delivered control. No parameter or dashboard action from C03 was demonstrated. If filtering, compute visible disagreement share as SUM(disagrees)/COUNTD(reference_id), with a positive denominator guard.

Derived ABC is computed upstream: rank customer units descending, original reference ascending for ties; use cumulative quantity **before** the reference, below 80%=A, below 95%=B, otherwise C. Do not replace it with a Tableau visible-percentile calculation after filtering.

## Error lessons and interpretation

Reported lesson: COUNTD states the unique business entity being counted. In the present one-reference-per-row table, COUNT and COUNTD agree; COUNTD does not fix duplicated quantity measures after a bad join. SUM(reference_id) is meaningless. Coloring by quantities while labeling counts needs explicit explanation; the delivered matrix uses count for both.

Repository check: 96 of 208 references differ, leaving 112 on the diagonal. That is classification disagreement, not an error rate: published basis/date may differ from extract unit volume. A few high-volume references can matter differently from many low-volume references.

*My learning summary:* I learned to define whether the visual counts entities or volume before choosing an aggregation. Comparing classifications is useful only when I preserve both methods and their limitations.
