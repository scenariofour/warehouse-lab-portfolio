Evidence: **O6, U1/U3, R1/R3; rebuild G** in the [register](../EVIDENCE_REGISTER.md). This sheet was added during delivery; it is not the blueprint's C04 rule register.

## Question and decision

Which sources account for the record population assigned to each governing size rule? A source/rule heatmap makes concentration easier to scan than the detailed token ledger. It helps direct definition-review effort to the appropriate source; it is not a quality score or proof that a rule is valid.

## Data, measures and web rebuild

Use [normalization_tokens.csv](../../public/normalization_tokens.csv), one original token per source/field. token_id is the source-table key; **source_id × rule_id** is the display grain after aggregation. Both are String/discrete dimensions. token_records and token_units are whole-number measures.

1. Set Rows to source_id and Columns to rule_id. Use Square/Highlight Table marks. This is an equivalent source/rule matrix rebuild; exact shelf orientation is not exported.
2. Place SUM(token_records) on Color **and Label**. Put SUM(token_units) on Tooltip, with source/rule and an explicit unit label. This color/label/tooltip encoding is visible in the published worksheet description.
3. Include the governing token rules HALF_SIZE, NUMERIC and RETAIN; use a consistent color scale. No custom threshold, parameter or filtering action is confirmed. Do not invent a pRule action simply because the heatmap can be selected.
4. Keep C01 beside the heatmap on Dashboard 02: the matrix locates a population; the ledger explains its token mappings. If adding a future selection action, record its exact source/rule target mapping and clear behavior before calling it implemented.

## Error lessons and scope

Diagnostic patterns: COUNT(token_id) measures distinct token groups, not source records; SUM(token_units) measures requested/picking quantity, not rows. A color change without a label/unit change can silently switch the question. A continuous source/rule pill creates the wrong layout: categories belong in discrete headers.

The token extract has three governing size-rule labels. The separate transformation_rules extract declares nine broader representation/retention/scenario rules; this heatmap is not a nine-rule compliance matrix. Every source record contributes to one governing token row, but foundational PARSE/TRIM rules also apply and are not separately counted here.

*My learning summary:* I learned to choose the measure before choosing a color scale. The heatmap tells me where to look; C01 and the evidence contract tell me what the rule means.

## Three self-checks

1. **What does a dark cell mean?** More source records assigned to that governing token rule, under the chosen scale; not more confirmed errors.
2. **Why SUM(token_records)?** Each extract row already contains a count of contributing source records.
3. **Is a C01b → C01 action confirmed?** No. The two panels are visible, but that interaction remains untested.

QA: cell totals, tooltip values, source scopes, legend readability and any future action. The 38846 HALF_SIZE customer-record total is repository-verified, not a comprehensive rendered-cell audit.
